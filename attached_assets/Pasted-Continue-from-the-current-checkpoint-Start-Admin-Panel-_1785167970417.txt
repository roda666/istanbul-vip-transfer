2. Authentication and security

Create:

- /admin/login
- protected /admin routes
- secure session handling
- logout
- session expiration
- server-side authorization checks

Requirements:

- No public registration.
- No default username or password in the repository.
- Never print passwords, hashes, tokens or secrets in logs.
- Passwords must be securely hashed with a maintained library compatible with the runtime.
- Protect every admin API route server-side.
- Use secure, httpOnly and sameSite cookies where applicable.
- Add login rate limiting.
- Prevent open redirects.
- Validate and sanitize all submitted data.
- Prevent stored XSS in content rendering.
- Add CSRF protection using the selected authentication framework’s supported method.

Create a secure admin creation script that:

- Reads ADMIN_EMAIL and ADMIN_PASSWORD from environment secrets.
- Creates the first admin only if no admin exists.
- Never accepts the password as a visible command-line argument.
- Never logs the password.
- Clearly tells the user to remove ADMIN_PASSWORD from secrets after the account is created.

Use AUTH_SECRET and DATABASE_URL only from environment variables.

4. Approval and scheduled publication rules

Enforce these rules in the database and server-side application logic:

- AI suggestions can only create RESEARCH or DRAFT records.
- AI-generated content can never directly become PUBLISHED.
- Only an authenticated active admin can approve content.
- Approval must record approvedBy and approvedAt.
- Only APPROVED content can be scheduled.
- Scheduled content becomes publicly eligible only when:
  approvedAt is present,
  approvedBy is present,
  scheduledAt is less than or equal to the current server time.
- If approved or scheduled content is edited, clear its approval and return it to REVIEW.
- Archived, draft, research and review content must never appear publicly.
- Store and display all scheduling times using Europe/Istanbul for the admin interface and UTC in the database.
- Record approval, scheduling, editing and publication actions in AuditLog.

Do not depend on a cron job for the basic publication gate. Public visibility must be determined safely from approval state and scheduledAt. A scheduler can be added later for notifications and cache revalidation.
