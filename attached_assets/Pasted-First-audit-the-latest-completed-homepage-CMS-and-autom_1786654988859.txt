PART 5 — TRANSLATION WORKFLOW

Turkish remains the canonical source language.

When Turkish homepage or other CMS content changes:

1. Save the Turkish version.
2. Detect exactly which translatable fields changed.
3. Create translation jobs for the selected target languages.
4. Preserve approved translations whose source fields did not change.
5. Mark affected translations as needing review.
6. Allow:
   - translate all eight target languages,
   - or manually select target languages.
7. Require approval before public publication by default.
8. Support bulk approval and bulk publication only for reviewed translations.
9. Show clear progress and useful per-language errors.
10. Never return an empty response body where the frontend expects JSON.

Shared fields such as media path, visibility, ordering, IDs and layout options must be synchronized without translation.

PART 6 — LOCALE NAVIGATION AND FALLBACK

Language switching must:

- preserve the equivalent current route,
- persist across internal navigation,
- work when switching back to Turkish,
- never redirect to 0.0.0.0 or a fixed development host,
- use relative URLs or the current request origin,
- preserve query parameters and hash where appropriate.

Fallback rules:

- Never display a mixed-language public page.
- If a localized page is unavailable, use a controlled Turkish fallback or redirect with correct locale behavior.
- Admin must visibly identify missing translations.
- Public UI must not display internal translation-status information.

Arabic requirements:

- full RTL layout,
- navigation and grids mirrored correctly,
- phone numbers, email addresses, IST, SAW, URLs, Mercedes Vito, Sprinter and other technical tokens remain LTR.
